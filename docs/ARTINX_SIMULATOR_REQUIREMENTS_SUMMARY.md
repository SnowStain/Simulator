# ARTINX Simulator 修改需求总结

更新时间：2026-05-08

本文档汇总本轮持续开发中提出的主要修改需求，用于后续开发者或 AI 继续推进项目时快速理解目标、约束和已形成的设计方向。

## 1. 房间与大厅流程

- 删除旧的 5v5 选车大厅链路，统一改为房间大厅布局。
- 单人、本地房间、局域网房间都应走同一套 OpenGK/房间式入口，不再回到旧大厅。
- 本地模式登出应回到主菜单或本地房间页，不得回旧大厅。
- 本地房间点击座位添加角色、添加 AI、切换玩家/AI/空位不能闪退。
- 房间内添加机器人或准备阶段切换点位不能卡几秒，不能每次完整重建世界或重复加载地图资源。
- 房间座位是机器人存在与否的唯一来源：
  - 添加了多少机器人，局内就只存在多少机器人。
  - 未启用机器人不能只是隐藏，正式对局中必须从 `World.Entities` 移除。
  - 未启用机器人不能出现在小地图、HUD、AI、弹丸、碰撞、网络快照里。
- 本地房间必须只允许一个本地玩家控制机器人，其余可为空或 AI。
- 单人模式也需要准备阶段，可配置出生点位/车辆构型，默认 60s，允许 Enter 跳过。

## 2. 局域网与联机同步

- 局域网准备时间和裁判系统自检阶段都可以呼出 P 菜单。
- 裁判端 P 菜单必须可关闭，点击响应不能卡顿。
- 本地模式玩家使用 O 键呼出一个面板，功能直接复用联机裁判端 P 面板。
- 多人模式 P 菜单用于改配置，不再改车型；车型在赛前准备阶段选择。
- 客户端进入游戏后按钮、输入不能无响应。
- 主机端必须拥有客户端控制机器人的实体，客户端移动后主机不能缺实体。
- 主机 authoritative snapshot / digest 中实体数量必须等于活跃座位机器人数量。
- UC/非 1v1 联机不应因为输入序号不连续而空步进，应复用最近的远端输入。
- 局域网日志需要可诊断 roster、snapshot、input、digest、pose drift、实体数量等问题。

## 3. 对局启动与裁判流程

- 本地模式也添加裁判系统自检时间，需求中明确过 15s 自检。
- 单人模式准备阶段 60s，可 Enter 跳过。
- 准备、自检、倒计时、Live 状态需要清晰切换。
- P/O 面板关闭后必须禁用鼠标交互区域，不能隐藏了仍可点击。
- P 面板登出：
  - LAN 裁判回房间页。
  - 本地房间回本地房间页。
  - 普通本地/单人回主菜单。

## 4. 玩家控制与死亡复活

- 玩家只能控制一个机器人。
- 被击杀后不切换视角，保持原本位姿，画面变灰并显示复活读条。
- 复活读条结束后不直接回出生点。
- “复活点”命名改为“出生点”。
- 复活后需要去自家补给区解锁枪管。
- 复活流程包含无敌与虚弱状态，按 `规则/复活机制/image.png` 对齐。
- 顶部 UI 如果某机器人没有控制源，不显示该机器人栏。

## 5. 机器人碰撞与移动

- 机器人碰撞体应尽量与 GPU 渲染看到的外观一致。
- 碰撞体应复用机器人外观/py 编辑器输出的形状参数，而不是手工拼一套不匹配的静态盒。
- 碰撞体要随车体角度、云台角度、腿部姿态、轮子和连杆姿态动态变化。
- 平衡步兵轮子碰撞体应是横向圆柱，连杆碰撞体应贴合视觉连杆。
- 全向轮、平衡步兵不能因为碰撞过严导致无法行动。
- 需要比对提交 `bfa274a8491102e732a8eeb9f1bf014024288ab1`：
  - 旧版移动性更好但容易穿墙。
  - 新版更严格但会卡住。
  - 目标是保留新版垂直/地形判定与动态轮腿，同时降低主体过度碎片化带来的卡死。
- 可通过地块判定必须先处理垂直落差是否可通过，再处理水平是否可通过，避免轮子爬上过高台阶导致车体瞬移。
- 编辑器中绘制的 collision 碰撞体积必须在局内真正参与碰撞。
- 名字或角色包含 `collision` / `碰撞` 的固定组件也应作为碰撞体参与局内计算。

## 6. 地图、资源加载与性能

- 完整游戏进程内地图资源、runtime grid、appearance catalog 等应提前加载并复用。
- 进入同一完整游戏进程后，不应因房间座位、出生点、准备确认反复加载地图。
- 点击加入房间、选择模式创建房间不能卡很久。
- 客户端进游戏不能严重卡顿。
- AI 路线规划不能造成帧率明显卡顿。
- AI 导航应降低帧内重规划和 A* 扩展压力，优先复用路径、限流计划任务。
- 长期无用代码文件应清理，例如已废弃的 Python 地图编辑器链路，保留 C#/OpenGK 主流程。

## 7. UI 与 HUD

- 顶部 UI 要显示基地和前哨站血量，并带数字。
- 当前要求是只显示当前基地/前哨站血量，避免数字与血条互相遮挡。
- 血量数字必须有清晰层级，不能被血条填充色吞掉。
- 小地图只显示实际存在的机器人。
- P/O 面板响应要快，关闭要可靠。
- 房间页、局内页、准备页不应出现旧大厅 UI。

## 8. 基地、前哨站、堡垒与增益

- 基地护甲在 2000 血以下要展开，样式参考 `规则/基地建模/3.png`。
- 200 血等低血量状态必须直接显示完全展开，不能还保持闭合。
- 基地中部装甲板左右两侧命中判定要正确，打中要有命中提示。
- 顶部 UI 显示基地/前哨站血量时不能被血条遮挡。
- 堡垒启用后，占领堡垒需要读条。
- 机器人站在堡垒区域时应能触发堡垒占领/增益，不应因角色或时间门槛无反馈。
- 梯形高地等 buff 区域中，F3 显示已在区域内时必须能触发增益。
- 按已经确定好的 buff 位置，继续按 `规则/增益` 完善功能。
- 血量机制、增益、性能体系要按 `规则/血量机制.png`、`规则/增益`、`规则/性能体系` 对齐。

## 9. 性能体系与配置

- P 面板中的底盘类型和发射机构类型用于配置性能体系。
- 步兵：
  - 底盘类型：血量优先 / 功率优先。
  - 发射机构类型：爆发优先 / 冷却优先。
- 英雄：
  - 底盘与发射机构指向同一配置：近战优先 / 远程优先。
- 工程：
  - 只显示底盘类型，不显示发射机构。
- 其他无差异配置显示默认。
- 所有升级和配置改动机器人血量时，要按血量比例缩放，不是维持旧数值。

## 10. 自瞄与发射

- 英雄自瞄不能卡顿。
- Q 自瞄能量机关时，发射不受普通单发间隔限制，但频率不超过 25Hz。
- 能量机关自瞄需要更顺滑，发射、命中反馈、能量机关状态要闭环。

## 11. 项目延续约定

- 修改前先定位所属子系统，避免大范围盲改。
- 房间/准备阶段不得走完整资源加载管线。
- 局内正式对局中未启用机器人必须不存在。
- 碰撞调试显示、实际碰撞、GPU 外观应尽量一致。
- 每轮修复后执行：
  - `dotnet build src/Simulator.ThreeD/Simulator.ThreeD.csproj -c Debug --no-restore`
  - 同步到 `build_verify/launcher_builds/debug/threeD`
- 继续维护并提纯 skill，让后续 AI 能理解房间、LAN、裁判、碰撞、RMUC 规则和性能优化的推进方式。
